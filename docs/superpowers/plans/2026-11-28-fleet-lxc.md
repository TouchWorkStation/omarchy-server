# Fleet LXC placement Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create and manage system containers on any connected physical swarm machine (not only this server), with NixOS config shares living on the host that runs the guest.

**Architecture:** Mirror remote VM hosting: connector/helper exposes Incus verbs on the computer; Server `containers.*` accept optional `hostId`; list merges local + remote; config dirs are created on the remote host’s data path via swarm file/RPC helpers. NixOS share-apply from Plan 4 reuses the same mount once the remote Incus disk device points at that host-local directory.

**Tech Stack:** Existing swarm remote-guest / connector patterns (`omarchyd/remote-guest-*.mjs`, `connector/`), Incus on each host.

**Spec:** `docs/superpowers/specs/2026-11-28-nixos-share-apply-design.md` (Fleet LXC placement)  
**Depends on:** Server LXC APIs stable; for NixOS-on-remote, Plan `2026-11-28-nixos-lxc-share-apply.md`. Remote Incus plumbing can start before NixOS.

## Global Constraints

- Branch `feat/fleet-lxc`.
- Tabs, no semicolons, single quotes. No version bump.
- Do not invent a second container runtime; Incus per-user mode on the computer (same security story as server).
- Refuse create with plain-language setup if Incus missing on the target host.
- Config share path on remote: connector-managed directory (document exact path in Task 2), not the server’s `dataDir`.
